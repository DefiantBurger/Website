## Class Scheduler

Semester planner that validates prerequisites and draws them as a dependency graph.

Its data ships with the build, from `frontend/src/content/scheduler/`: `course_data.json` (the ~3 MB catalog) becomes a hashed asset that browsers cache for good, and `my_courses.json` (the default plan) is bundled into the JS. A catalog update reaches the site with the next deploy.

### Data Model

**Schedule.** Keys are `precollege` (credit already earned) or a term plus two-digit year (`fall24`, `winter25`; terms are `winter`, `spring`, `summer`, `fall`). Columns are always sorted by date regardless of key order; any other key is rejected. A `[n]` suffix sets the credits for a variable-credit course.

```json
{ "semesters": { "precollege": ["MATH 221"], "fall24": ["MATH 222", "PHYSICS 499[3]"] } }
```

**Catalog.** Version 2, generated by the separate `course-data-scraper` repo (its README is the full spec); any other `version` fails to load. Each course has `title`, `credits` (or `min_credits`/`max_credits`), `requires`, `requisites_text`, `not_open_with_credit_for`, and `last_taught`.

- `requires` is `null` or `{"all": [...]}`; each item of that top-level `all` is a **requirement row**. Nodes are a course code, `{"all": [...]}`, `{"any": [...]}`, or `{"atleast": k, "of": [...]}`, nested to any depth. `"concurrent": true` (only on `any`) allows same-semester enrollment for anything under it.
- `requisites_text` keeps conditions the scheduler can't check (standing, major, consent). It isn't displayed.
- `not_open_with_credit_for` is treated as symmetric, since the catalog usually lists a pair on one side only.
- `times_offered` (`{"Fall": n, "Spring": n}`) counts the terms of each season a course ran in during the top-level `offered_window` (`{from, to, Fall, Spring}`, where `Fall`/`Spring` are the maximum counts). Read the maxima from the file; the window grows with new data. A course with both counts 0 has unknown history (independent study, summer-only, not run lately), not "never offered". `terms_offered` and `last_taught` are loaded but unused.

### Updating the Catalog

The catalog is a snapshot of [guide.wisc.edu/courses](https://guide.wisc.edu/courses/), so regenerate it each term. The scraper lives in [`course-data-scraper`](https://github.com/DefiantBurger/course-data-scraper), cloned next to this repo:

```bash
uv run main.py fetch --refresh     # re-download the subject pages
uv run main.py build               # writes output/course_data.json and output/report.md
uv run main.py diff ../PersonalWebsite/frontend/src/content/scheduler/course_data.json output/course_data.json -v
cp output/course_data.json ../PersonalWebsite/frontend/src/content/scheduler/
```

- Requisite text is parsed by a rule parser that refuses anything ambiguous; refused strings get hand-written entries in its `data/overrides.json`, and until then export with no requirements. `report.md` lists unresolved strings, stale overrides, and dropped references; check it before copying the file over.
- Non-course conditions (standing, consent, placement) and courses missing from the catalog are dropped, so a dropped alternative makes a requirement stricter.
- Unknown courses in saved plans are skipped on load, so a catalog update doesn't break old links. `my_courses.json` (the default plan) isn't generated; check it still loads cleanly after an update.

### Behavior

- **Code layout.** `catalog.ts` builds and exports schedules (each course occurrence gets a unique ID, `<course>__<n>`) and searches the catalog. `schedule.ts` holds every edit as a pure function. `store.svelte.ts` (`SchedulerStore`) holds the page state (the schedule as undo history, the catalog, selection, notices, drag state), applies edits through `store.apply()` so `history.ts` can undo/redo (100 steps), and derives everything else (graph, overlaps, problems). `UtilityScheduler.svelte` creates the store, passes it to the components, and handles loading, import/export, and the share link.
- **Requirement checks** (`logic.ts`). Each row is evaluated against a course's earliest scheduled instance: `met`, `concurrent`, `out-of-order`, or `missing`, ranked in that order. `any` takes its best child, `all` its worst, `atleast k` its k-th best. Edges are drawn from the courses that decided each row. Precollege courses count as earned, so their own requirements aren't checked. Progress is satisfied rows ÷ all rows.
- **Credit overlaps.** For a pair that can't both count, the later one is flagged and both cards show `≠`; pairs entirely in precollege are ignored.
- **Offering warnings** (`offering.ts`). A soft warning, never a block, since the counts are history, not the official schedule. A course in a Fall or Spring column is flagged `∅` when it ran in none of that season's terms but some of the other's, and `~` when its rate for that season is under half its rate for the other. A relative rule, so courses that run in about half of each season (often new ones) aren't flagged. Courses with no history, winter and summer terms, and terms before the current one (a course already taken was clearly offered) are skipped. Warnings show in the Problems panel and on the card, and the details panel shows each course's counts.
- **Auto-detangle** reorders cards within columns (barycenter sweeps) to reduce edge crossings.
- **Share links** (`shareLink.ts`). The plan lives in the URL fragment as `#plan=v1.<base64url(deflate-raw(JSON))>`, so it never reaches the server. After the first edit, every change is written with `history.replaceState` (debounced 300 ms). Opening a link skips auto-detangle so card order is kept. Decoding is capped at 256 KB. **A new format needs a new version prefix, and the `v1` decoder must stay** so old links still open.
- **Validation** is shared by links and JSON import. Bad semester keys or a malformed file reject the whole plan; unknown courses and invalid credits are skipped and listed in a notice, so old links survive catalog changes. An undecodable link on page load shows an error and falls back to the default plan.

## File Share

Temporary file sharing keyed by an access key: the browser encrypts each file and its name before uploading, and files expire after 10 minutes.

### API

`POST` bodies are `multipart/form-data`. `token` is the lookup token the browser derives from the access key (see Encryption below); the server never receives the key itself.

| Method | Path | Fields | Response |
| --- | --- | --- | --- |
| GET | `/api/fileshare/status/` | | `{activeFileCount, usedBytes, maxFileBytes, maxTotalBytes, retentionSeconds}` |
| POST | `/api/fileshare/upload/` | `file` (ciphertext), `token`, `salt`, `encryptedName`, optional `replace=1` | file record; `replace=1` deletes the token's earlier files once this one is stored |
| POST | `/api/fileshare/list/` | `token` | `{"files": [<file record>]}`, oldest first; 404 if none |
| POST | `/api/fileshare/access/` | `token`, `id` | the stored ciphertext as an `application/octet-stream` attachment |

A file record is `{id, salt, encryptedName, sizeBytes, uploadedAt, expiresAt}`. `id` is random; `sizeBytes` is the plaintext size, worked out from the ciphertext's.

Errors: `400` missing file, malformed token, salt, or name, or a body whose size no encryption produces; `404` no matching file; `413` file over 80 MB; `429` too many uploads in flight (Nginx: 2 per visitor, 6 in total); `503` too many concurrent transfers.

### Behavior

- **Encryption** (`lib/fileshare/crypto.ts`, in the browser). PBKDF2-SHA256 (600,000 iterations, with a fixed site-wide salt, since whoever downloads has only the key) turns the trimmed, NFC-normalized access key into a master key. HKDF derives the lookup token from it and, with a random 16-byte salt per file, separate AES-256-GCM keys for the file's content and its name. Content is encrypted in 1 MiB chunks; each chunk's nonce is its index plus a last-chunk flag, so truncated, extended, or reordered payloads fail to decrypt. Names are padded to 256 bytes so their length doesn't show, and cleaned (directories and control characters removed) by both uploader and downloader. Files are encrypted and decrypted whole in memory, which the 80 MB cap keeps reasonable. WebCrypto exists only in a secure context, so the page needs HTTPS or `localhost` (the dev server opened by LAN IP fails).
- **What the server sees.** The token, ciphertext, and each file's salt, encrypted name, size, and upload time; never the key, a filename, or contents. Cloudflare, which terminates TLS, sees the same. A weak key can still be brute-forced from its token at one PBKDF2 run per guess, and the encryption is only as trustworthy as the JavaScript the server sends.
- **Generated keys.** Generate fills in six words from EFF's short word list (`lib/fileshare/wordlist.ts`, 1,295 words, so ~62 bits), loaded on demand, and shows it in full with a copy button, since six words overflow the field on a phone.
- **Storage.** The index of files lives in memory (`FileShareStore`, one per app); each file's ciphertext is `<instance>/fileshare/<id>`. Nothing survives a restart (deploy, reboot, or crash): creating the store empties that directory, since without the index, which holds each file's salt and encrypted name, the payloads could never be found or decrypted. This assumes one process, as Waitress runs it.
- **Lookup.** A file belongs to the token whose HMAC-SHA256, keyed with `SECRET_KEY`, matches its label, so the index never holds a usable token.
- **Limits.** 80 MB per file (under Cloudflare's 100 MB request limit), and 1 GB and 1,000 files in total; the oldest files are evicted to make room. At most 3 transfers run at once (`MAX_CONCURRENT_TRANSFERS`), leaving one of Waitress's 4 threads for other requests; a download keeps its slot until the response is fully sent.
- **Expiry.** File-share requests delete expired files, and in production a background thread (`start_expiry_sweeper`, started in `main.py`) also sweeps every minute. Expired, evicted, and replaced files are deleted from disk immediately.
- **Downloads** are always `application/octet-stream` with `nosniff`, so nothing uploaded can run on the site's origin.
- **UI batches.** The UI derives the key once, then encrypts and uploads one request per file, with a progress bar for the whole batch, and the first sends `replace=1`, so a new batch replaces the key's previous files. If the first upload fails, the previous files stay; if a later one fails, the key keeps only the files stored before it.

## Message Board

Anonymous board where messages expire 60 seconds after posting.

| Method | Path | Body | Response |
| --- | --- | --- | --- |
| GET | `/api/messageboard/messages/` | | `{messages, serverTime, retentionSeconds, maxMessageLength}`, messages newest first |
| POST | `/api/messageboard/messages/` | JSON: `{"text": "..."}` | `201` with the message |

A message is `{id, text, createdAt, expiresAt}`. Errors: `400` empty, non-string, or over 280 characters after sanitizing; `413` body over 16 KB; `429` over 5 posts in 10 seconds from one IPv4 address or IPv6 /64.

- **Sanitizing.** Normalizes line endings to `\n`, turns tabs into spaces, NFC-normalizes, and drops control, format (zero-width, bidi overrides), surrogate, private-use, unassigned, and line/paragraph-separator characters, except the joiner and tag characters emoji sequences need. Markup is stored as typed; the frontend renders text, never HTML. Runs of 3+ newlines collapse to 2.
- **Storage.** In-process memory behind a lock: at most 200 messages (oldest evicted), expired ones purged on every read and write, all lost on restart.
- **Rate limit.** 5 posts per 10 s per client IP (sliding window), checked before validation, so rejected posts count too.
- **Page.** Polls every 5 s while the tab is visible (and right away when it becomes visible again), and after posting. Each card counts down and disappears when it expires. Expiry is timed from `serverTime`, so a wrong local clock doesn't hide or keep messages (`lib/messageboard/board.ts`). Messages are never rendered with `{@html}`.
- **Length.** The page counts code points after NFC, like the server, so an emoji counts once. The textarea has no `maxlength`, which counts UTF-16 units.

## Adding a Utility

1. Add the route (`routeDefinitions.ts` + `routes.ts`) and the page in `frontend/src/pages/`, with its logic and API client in `frontend/src/lib/<name>/` built on `lib/api.ts`.
2. Add a card to `Utilities.svelte`.
3. Add backend routes under `/api/<name>/` in `views.py` (logic in its own module; raise an `ApiError` subclass for client errors) with tests.
4. Document it here.
